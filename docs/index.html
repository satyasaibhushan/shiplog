shiplog

A ledger of what you actually built. shiplog reads your GitHub commits, PRs, and diffs, deduplicates them, and uses an LLM (Claude or Codex) to write the human-readable story of your work — entirely on your machine.

§ 01

Vision & Roadmap

shiplog is growing from a summary generator into a complete, curated record of an engineering career — the log a captain keeps, not the wake the ship leaves.

  1. North Star

    A career-long work log

    Backfill and maintain a log of everything built over the last 4 years across company repositories. Every entry accepts review comments, so summaries are regenerated until the output matches what actually happened. The log is curated, not just generated.

  2. CLI Ready

    Automated reporting routines

    Scheduled Claude/Codex routines generate a report every day and every week covering what shipped in that window — no manual triggering. The log writes itself; you only review. The primitive exists: shiplog report --daily / --weekly saves the logs and prints the report — a scheduler just has to call it.

  3. CLI Ready

    Timerange reports, project-wise

    Given any date range, produce a report of all work done in that range, grouped by project — ready for performance reviews, appraisal cycles, or handoffs. Available today as shiplog report -f <from> -t <to>.

  4. Future

    Task Finder integration

    Task Finder is a companion desktop app that aggregates work items from Jira, Gmail, and Slack into one prioritized task list. Syncing shiplog task-wise against it captures the work GitHub never sees — client tickets, one-off data requests — and gives the code produced across repos its business context.

Persistence — decision deferred. Everything currently lives in plain local files: JSON entities under ~/.shiplog-data/ plus the SQLite cache at ~/.shiplog/cache.sqlite. There is no git sync or remote datastore. A proper datastore (durable journal vs disposable cache, backup story) will be chosen once the reporting workflows above have settled — the file layout is good enough until then.
§ 02

Quick Start

shiplog is not published to npm yet (the shiplog package on npm is an unrelated project) — install from source.
git clone https://github.com/satyasaibhushan/shiplog
cd shiplog
bun install
bun run build:all
bun link          # registers a global `shiplog` command

shiplog

This opens a local web UI at http://localhost:3847 where you select date ranges and repositories, then generate AI summaries.

§ 03

Usage

Web UI (default)

shiplog                          # Opens browser at localhost:3847
shiplog --port 8080              # Custom port
shiplog --no-browser             # Start server without opening browser

Reports (persisted)

shiplog report runs the full pipeline for each repo, saves a log per repo (plus a rollup across them) so everything shows up in the web UI, and prints a project-wise markdown report to stdout. This is the building block for scheduled daily/weekly routines:

# Set the repos to track once
shiplog config trackedRepos owner/repo1,owner/repo2

shiplog report --daily                       # today's work
shiplog report --weekly                      # last 7 days
shiplog report -f 2024-01-01 -t 2024-03-31   # any range, project-wise

# One-off overrides
shiplog report --weekly -r owner/other-repo --title "Sprint 42"
shiplog report --daily -o json > report.json

Repos with no activity in the range are skipped. A rollup (the cross-project overview) is only created when two or more repos had activity.

Headless CLI (one-off, nothing saved)

Generate a report without a browser and without persisting anything:

# Markdown output
shiplog -o markdown -r owner/repo -f 2024-01-01 -t 2024-03-31

# JSON output (pipe to file)
shiplog -o json -r repo1,repo2 -f 2024-01-01 -t 2024-03-31 > report.json

# Standalone HTML report
shiplog -o html -r owner/repo -f 2024-01-01 -t 2024-03-31 > report.html

§ 05

How It Works

  1. You run shiplog
  2. Fetches your GitHub repos via gh CLI
  3. You select date range, repos, scope
  4. Fetches commits + PRs + diffs
  5. Deduplicates by patch-id (catches cherry-picks)
  6. Groups into PR groups + orphan clusters
  7. Summarizes each group via LLM (map phase)
  8. Creates roll-up summary (reduce phase)
  9. Displays interactive results in browser

Caching

All data is cached in ~/.shiplog/cache.sqlite:

  • Commit diffs cached by SHA — immutable, never re-fetched
  • LLM summaries cached by content hash — skips the LLM on repeat runs
  • Re-running the same query is near-instant after the first run

Scope Filters

  • Merged PRs — completed, shipped work
  • Open PRs — work in progress
  • Closed PRs — abandoned / rejected PRs
  • Direct commits — pushes not part of any PR

§ 07

Development

git clone https://github.com/satyasaibhushan/shiplog
cd shiplog
bun install

# Build the frontend (use build:all, not build)
bun run build:all

# Run in dev mode
bun run start          # or: bun run dev (hot reload)
Build the web assets with bun run build:all, not bun run build. build only emits main.js and styles.css; build:all also copies index.html into dist/web/ — without it the page returns 404. Note that dev/start do not rebuild assets; re-run build:all after changing anything under src/web/.

Running from source

When running from a cloned repo, pass subcommands through the start script:

bun run start setup            # = shiplog setup
bun run start config llm codex # = shiplog config llm codex

Or link the package globally with bun link. If you then get command not found: shiplog, add bun's global bin directory to your PATH:

export BUN_INSTALL="$HOME/.bun"
export PATH="$BUN_INSTALL/bin:$PATH"
